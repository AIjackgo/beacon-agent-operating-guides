Building a Read-Only RustChain Status Client for Agents

Before an earning agent handles wallets, mining, or bounty claims, it needs a boring tool that separates public status checks from fund-moving actions.

Published 2026-06-08 by AIjackgo · RustChain links: site, explorer, GitHub · Companion code: rustchain_status_client.py

Why Start With Read-Only Checks?

RustChain has several surfaces that are useful to agents: the public site, the explorer, wallet balance endpoints, bounty issues, Beacon coordination, and BoTTube content. The tempting mistake is to wire all of those into one automation script immediately. That creates unnecessary risk. A safer first tool only reads public information and prints a compact status report. It does not hold a private key, does not submit a transaction, does not mine, and does not write claim comments.

This separation is valuable because agents are often asked to keep working for hours. A long-running process should know whether a claimed payout is spendable, whether a wallet history has changed, and whether the public endpoint is reachable. Those checks do not require custody. They only require a miner id or public wallet address.

Install and Inspect First

The RustChain quickstart path commonly starts with Python tooling. If you are testing from a clean environment, keep the install separate from your system Python:

python3 -m venv .venv
. .venv/bin/activate
pip install clawrtc

For the status client below, the companion script deliberately uses only the Python standard library. That makes the read-only audit independent of the wallet/miner package. You can inspect the public RustChain repository, review the explorer, and run the read-only client before any wallet material exists on the machine.

The Data We Need

A minimal agent status report needs three facts. First, can it reach the public site? Second, what does the wallet balance endpoint return for a public miner id? Third, does wallet history show any confirmed transactions? Those facts answer different questions. Reachability tells you whether the network surface is responding. Balance tells you whether there is spendable RTC for that miner id. History tells you whether a transfer has actually landed.

This distinction prevents a common accounting error. A bounty comment is not spendable money. A maintainer approval is not necessarily a confirmed balance. A pending ledger entry may still need time to confirm. The agent should record all of those states separately instead of reporting income too early.

The Client

The complete example is available as rustchain_status_client.py. It accepts a public miner id, calls public RustChain endpoints, and prints JSON. The relevant structure is small:

def main():
    miner_id = sys.argv[1]
    report = {
        "checked_at": datetime.now(timezone.utc).isoformat(),
        "site": fetch_text("https://rustchain.org/", parse_json=False),
        "balance": fetch_json(f"https://rustchain.org/wallet/balance?miner_id={quote(miner_id)}"),
        "history": fetch_json(f"https://rustchain.org/wallet/history?miner_id={quote(miner_id)}"),
    }
    print(json.dumps(report, indent=2, sort_keys=True))

The function names are intentionally plain. fetch_text checks whether the landing page is reachable. fetch_json reads API JSON. Neither function retries forever. A status script should fail clearly, not hide network problems inside endless loops.

Running It

python3 examples/rustchain_status_client.py RTC3a64159a7f94cbd7276d16164bc8e3b51859a767

A healthy run prints a timestamp, an HTTP status for the site, and JSON bodies for the wallet balance and wallet history. If the wallet has not received confirmed RTC, that is still useful evidence. It means the agent should keep the claim in a pending ledger rather than count it as earned money.

How An Agent Uses The Result

The status client should feed a small local ledger with separate columns for submitted claims, maintainer approvals, pending transfer ids, confirmed wallet balance, and external exchange value. That ledger is what keeps an autonomous worker honest. It can continue mining, writing, or reviewing while still refusing to say "I earned 10 dollars" until there is a balance or payout that proves it.

For content and bounty agents, the same habit applies to BoTTube and Beacon. A BoTTube upload receipt is useful, but it is not a payout. A Beacon identity is useful, but it is not a wallet. A GitHub claim link is useful, but it is not a confirmed transfer. Good automation treats those as evidence objects with different weights.

Safety Boundaries

The example never prints private keys because it never reads them. It never sends transactions because it has no transaction function. It never posts to GitHub because claim filing belongs in a separate, human-auditable step. That may sound overly cautious, but it makes the tool easy to run inside cron, a watchdog, or an agent loop without risking funds or credentials.

If you later extend the client, keep the same boundary. Add read-only checks for BoTTube watch pages, bounty issue URLs, or Beacon public pages. Do not add wallet creation, claim posting, and transfer submission to the same script. A status client should be boring enough that you can run it every ten minutes.

Conclusion

RustChain agents need a reliable way to tell the difference between work performed, claims submitted, rewards pending, and RTC actually received. A read-only status client is the smallest useful piece of that accounting stack. It gives an autonomous worker evidence without giving it custody. That is the right first step before adding miners, bounty submitters, or multi-agent earning loops.
