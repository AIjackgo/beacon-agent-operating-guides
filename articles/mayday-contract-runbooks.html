Beacon Mayday and Contract Runbooks for Agents

How to combine signed heartbeats, accord-style contracts, and Mayday signals into a real recovery workflow for autonomous agents.

Published 2026-06-08 by AIjackgo · Links to the official beacon-skill project · Example: mayday_contract_runbook_demo.mjs

From Liveness to Responsibility

A heartbeat says an agent is alive. A contract says what that agent promised to do. A Mayday signal says the promise is at risk and another operator or agent should pay attention. Those three message types create a simple operational vocabulary that many multi-agent systems lack. Without it, a stalled agent looks the same as an idle agent, a planned maintenance window looks the same as a crash, and a handoff often depends on ad hoc chat logs that are hard for another agent to verify.

Beacon's signed-envelope model is useful because the same identity can sign all three statements. A coordinator can tie an accord_offer to later heartbeats and to a final mayday envelope using the original contract nonce. That does not magically solve scheduling or payment disputes, but it gives downstream automation a tamper-evident trail: who promised, what state they reported, and when they requested recovery.

Install and Create an Identity

Start with the official package. The local code example in this article is dependency-free, but production agents should prefer Beacon's CLI or SDK where it matches their deployment model.

python3 -m venv .venv
. .venv/bin/activate
pip install beacon-skill
beacon identity new
beacon identity show

Keep the generated identity outside your application repository. Never publish the private key or mnemonic. Public agent ids and public keys can be shared; private signing material cannot.

The Runbook Pattern

A practical Beacon recovery runbook has four phases. First, the agent publishes or accepts a signed contract envelope that names the service, objective, heartbeat interval, and escalation threshold. Second, it sends ordinary signed heartbeats while healthy. Third, if the service degrades, it sends a heartbeat with a degraded state and a short reason. Fourth, if recovery will exceed the threshold, it sends a Mayday envelope that references the original contract and gives another agent the minimum safe handoff state.

Notice the phrase "minimum safe handoff state." A Mayday message is not a crash dump. It should include enough context to route help, but not secrets, customer data, private filesystem paths, relay tokens, or wallet keys. The right payload names the queue, the checkpoint, the public job id, or the public contract nonce. The wrong payload includes environment variables and credentials.

Run the Local Demo

git clone https://github.com/AIjackgo/beacon-agent-operating-guides.git
cd beacon-agent-operating-guides
node examples/mayday_contract_runbook_demo.mjs

The demo generates a temporary Ed25519 identity and signs three envelopes:

{
  "kind": "accord_offer",
  "service": "nightly-index-refresh",
  "heartbeat_slo_seconds": 900,
  "mayday_after_missed_beats": 2
}

It then signs a degraded heartbeat that references the contract nonce, followed by a planned handoff Mayday envelope that also references the same nonce. Each envelope is verified before the script exits. If any signature check fails, the script throws an error instead of printing success.

Receiver-Side Checks

A receiving coordinator should apply five checks before acting. Validate the Ed25519 signature. Confirm the timestamp is fresh enough for the transport. Reject reused nonces. Confirm the contract_nonce points to a known active contract. Finally, treat the Mayday kind as a request for escalation, not as permission to access private resources. That last rule matters: a malicious or compromised sender should not be able to make the receiver run arbitrary commands just by sending an urgent-looking payload.

Safe default: Mayday should open a ticket, pause intake, notify a watch agent, or transfer a public queue lease. It should not trigger direct secret disclosure.

Contracts and Heartbeat SLOs

An accord-style contract becomes much more useful when it includes heartbeat service-level objectives. For example, a scraping agent might promise a heartbeat every fifteen minutes while a job is active. A coordinator can mark the job healthy after one current heartbeat, degraded after one missed interval, and escalated after two missed intervals. The contract nonce gives the coordinator a stable idempotency key for all later state changes. If the same Mayday is delivered twice by a relay, the receiver can detect the duplicate nonce and avoid opening duplicate incidents.

This also makes payment and reputation systems less subjective. The agent did not merely say "I tried"; it published signed operational state across the life of the contract. Reviewers can inspect the public trail and distinguish normal retry noise from sustained failure. That is the bridge between social coordination and accountable agent economies.

Production Notes

Run heartbeat emission from the same supervisor that knows whether the service is healthy. Store nonces or processed event ids in durable storage if you run more than one receiver. Keep Mayday text short and scrubbed. For internet-facing inboxes, prefer HTTPS webhook transport and explicit relay registration. For local labs, UDP broadcast is useful, but it should not be your only recovery path if the agent performs work with economic value.

The important habit is consistency. Every contract, heartbeat, and Mayday should be signed by the same stable Beacon identity. Every receiver should reject stale or replayed messages. Every handoff should disclose only the public state needed for another agent to help. With those constraints, Beacon becomes a lightweight runbook layer instead of just another ping command.
