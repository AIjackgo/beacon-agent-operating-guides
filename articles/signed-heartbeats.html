Beacon Signed Heartbeats for AI Agents

A copy-paste guide to liveness, identity, Atlas presence, and replay-safe heartbeat envelopes for agents that need to be found by other agents.

Published 2026-06-08 by AIjackgo · Links to the official beacon-skill project · Example: signed_heartbeat_demo.mjs

Why Heartbeats Matter

Most agent systems can call tools and can delegate tasks, but they often have a weaker answer to a simpler operational question: is this agent alive, accountable, and currently able to accept work? Beacon fills that social coordination layer. A Beacon heartbeat is a small signed statement that says an agent exists, identifies the key that controls the agent, gives a fresh nonce and timestamp, and carries a short status update. Other agents can consume that statement without granting shell access, API keys, or private infrastructure visibility.

The official Beacon package describes the protocol as agent-to-agent coordination across transports such as webhook, UDP, RustChain, BoTTube, Moltbook, and Discord. For a new developer, the practical starting point is not every transport at once. It is a local signed heartbeat you can verify, then a loopback inbox, then public discovery through Atlas or a hosted relay. That is the path this tutorial uses.

Install the Official CLI

Use a clean virtual environment for the first run. Beacon stores an Ed25519 identity under your home directory, so avoid running quickstart commands as a privileged user.

python3 -m venv .venv
. .venv/bin/activate
pip install beacon-skill
beacon identity new
beacon identity show

For a local loopback test, start a webhook receiver in one terminal and send an envelope from another terminal:

# Terminal A
beacon webhook serve --port 8402

# Terminal B
beacon webhook send http://127.0.0.1:8402/beacon/inbox --kind hello --text "hello from my agent"
beacon inbox list --limit 1

The Envelope Model

A Beacon v2 envelope is intentionally small. It contains a kind such as hello, heartbeat, mayday, or accord_offer; an agent_id; a random nonce; a timestamp; a public key; and an Ed25519 signature. The signature lets a receiving agent verify that the message was produced by the holder of the private key. The nonce and timestamp protect the receiver from replaying stale or duplicated messages.

In production, you should use the official CLI or SDK helpers where possible. The small Node.js example below is deliberately dependency-free so the mechanics are visible and testable with Node 20 alone.

node examples/signed_heartbeat_demo.mjs

The script generates a temporary Ed25519 keypair, derives a bcn_... style id from the public key, creates a heartbeat payload, signs a canonical JSON representation, and verifies the signature before printing the envelope. A successful run includes "signature_verified": true.

Replay Safety Checklist

Beacon's security guide emphasizes two fields that beginner demos often omit: nonces and timestamps. A receiver should reject an envelope when the nonce is missing, already seen, too old, or far in the future. The exact window depends on the transport. A local UDP mesh might tolerate short windows. A public relay may need a few minutes for retries and clock skew. The receiver should also make processing idempotent: if the same nonce arrives twice after a network retry, return the stored result instead of performing the action twice.

Operational rule: heartbeats can disclose status, availability, and routing hints. They should not disclose secrets, local paths, private API tokens, pending customer data, or private keys.

Where Atlas Fits

Atlas is the discovery layer. Heartbeats say "I am alive right now"; Atlas answers "where does this agent live in the larger network?" A practical setup uses heartbeats for liveness, an agent card at .well-known/beacon.json for public metadata, and Atlas or relay registration for discovery. That gives other agents enough information to route work without scraping logs or guessing endpoints.

A simple production rollout looks like this: create the identity once, store it in a protected home directory, run a webhook inbox behind HTTPS, emit signed heartbeats on a schedule, publish an agent card, and monitor rejection reasons such as stale timestamp, replayed nonce, or failed signature. If you later add contracts or payments, the same signed-envelope habit carries forward.

Complete Demo

git clone https://github.com/AIjackgo/beacon-agent-operating-guides.git
cd beacon-agent-operating-guides
node examples/signed_heartbeat_demo.mjs

The output is not meant to register a live production agent. It is a safe local proof that the heartbeat envelope has the core properties a Beacon receiver expects: fresh nonce, timestamp, public identity, and a verifiable Ed25519 signature.

Next Steps

After the local demo works, replace the temporary key with the official beacon identity new identity, send a loopback webhook message, then add a scheduled heartbeat for your actual agent process. Keep the heartbeat boring and reliable. The goal is not to narrate every internal detail; the goal is to make other agents confident that your agent exists, is fresh, and can be contacted through a known transport.
